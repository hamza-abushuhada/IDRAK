# IDRAK Connect Lab — كاشير ومتجر أونلاين للتجربة

تطبيق تجريبي مستقل بالكامل عن مشروع إدراك الحقيقي. يحتوي على **POS بسيط**، **موقع طلبات أونلاين**، **إدارة للطلبات والمرتجعات**، و**مستقبل Webhook محاكي لإدراك**.

**مهم:** شاشة استقبال الأحداث هي محاكي مستقل وليست مشروع IDRAK الأصلي. لن تظهر الفواتير تلقائيًا داخل لوحة IDRAK الفعلية إلا بعد إنشاء موصّلين حقيقيين في مشروع إدراك، والتحقق من التوقيع، وإجراء المطابقة ومنع التكرار. لا يوجد دفع إلكتروني حقيقي ولا ربط بأي POS أو موقع تجاري.

## التشغيل على Windows

1. فك ضغط ZIP في أي مجلد، مثل Documents.
2. افتح المجلد الناتج `idrak-connect-lab`.
3. **الطريقة الأسهل:** اضغط مرتين على `START_WINDOWS.bat`. إذا لم تعمل، اختر Open in Terminal داخل المجلد وشغّل:

```powershell
py -3 demo_server.py
```

إذا أمر `py` غير معروف، استخدم `python demo_server.py`.

افتح الروابط:

| الشاشة | الرابط |
|---|---|
| كاشير POS | http://127.0.0.1:8765/pos |
| متجر إلكتروني | http://127.0.0.1:8765/shop |
| إدارة الطلبات والمرتجعات | http://127.0.0.1:8765/admin |
| محاكي استقبال إدراك | http://127.0.0.1:8766/ |

**لا تحتاج Node أو Docker أو Supabase أو GitHub.** فقط Python 3.10 أو أحدث، وتشغيل الجهاز المحلي.

## تجربة كاملة

1. افتح الكاشير وأنشئ فاتورة نقدًا. تظهر فورًا في قسم الكاشير وفي محاكي الاستقبال بعد تحديث تلقائي بسيط للعرض.
2. افتح المتجر واطلب بالدفع التجريبي؛ يضاف طلب مختلف المصدر. لا يتم تحصيل مبلغ حقيقي.
3. جرّب الدفع عند الاستلام: يظهر الطلب Pending ولا يحسب إيرادًا محققًا حتى تضغط «تأكيد الدفع» في إدارة الطلبات.
4. من إدارة الطلبات، جرّب «تسجيل مرتجع»؛ سيُحدّث وضع الفاتورة، ويعود مخزون الأصناف.
5. من سجل إرسال الأحداث، اضغط «إعادة إرسال الحدث»؛ يرد المستقبل بـ `duplicate_skipped`، ولا تُحسب الفاتورة مرة ثانية.
6. أغلق الخادم بـ Ctrl+C ثم أعد تشغيله؛ تبقى الفواتير محفوظة في SQLite داخل `data/`.

**كل البيانات التجريبية في** `data/sources.sqlite3` و`data/simulated_idrak.sqlite3`؛ لا تدخل إلى قاعدة إدراك الحقيقية إطلاقًا.

## واجهات الربط الجاهزة

مصدر الكاشير:

```http
GET http://127.0.0.1:8765/api/pos/events?after=0&limit=50
```

مصدر المتجر:

```http
GET http://127.0.0.1:8765/api/web/events?after=0&limit=50
```

الرد يحتوي على `events` و`next_cursor` و`has_more`. لكل حدث `source.system` ثابت و`source.account_id` و`event_id` و`source_sequence` وبيانات الفاتورة، لمنع التكرار عبر إعادة الربط.

استعراض جميع الطلبات والمنتجات:

```http
GET http://127.0.0.1:8765/api/orders
GET http://127.0.0.1:8765/api/products
```

الحالات الممكنة: `pending`, `completed`, `cancelled`, `refunded`. لا تُحتسب `pending` أو `cancelled` أو `refunded` ضمن الإيراد المحقق في محاكي الاستقبال.

**التحديث اللحظي:** عند إصدار فاتورة أو تغيير حالتها، يرسل التطبيق طلب POST موقّعًا بـ HMAC SHA-256 إلى محاكي الاستقبال على `http://127.0.0.1:8766/ingest`. يرفض المستقبل التوقيع غير الصحيح ويمنع تكرار نفس `event_id`. لو لم يكن المستقبل شغّالًا، يحفظ المصدر الأحداث المعلّقة ويعيد إرسالها عند تشغيله أو عند «إعادة إرسال الأحداث المعلقة».

للتجربة الأولية لا توجد صلاحيات API؛ الخدمات تستمع على `127.0.0.1` فقط، وليس على الشبكة أو الإنترنت. **ليست مناسبة للإنتاج** دون مصادقة فعلية، إدارة أسرار، توثيق متكامل، حماية الطلبات والحدود، وجدولة retries.

## المطلوب من Claude لربطها بإدراك الأصلية

أرفقت ملف `CLAUDE_INTEGRATION_REQUEST_AR.md` وفيه طلب تنفيذ واضح وجاهز للإرسال إلى Claude مع هذا المشروع.


إنشاء موصّلين حقيقيين داخل `api/app/services/pos/` أو تحويل طبقة الربط إلى `connectors/` أكثر عمومية:

- `LabPOSAdapter` يسحب أحداث `/api/pos/events` ويطبعها إلى النموذج الموحّد.
- `LabWebAdapter` يسحب أحداث `/api/web/events` ويحوّل الطلبات الجديدة والمدفوعة والملغاة والمرتجعة إلى أحداث مالية صحيحة.
- تحويل `source.system + account_id + external_id` لهوية **ثابتة عبر فصل الاتصال وإعادة ربطه**. لا تجعل `connection_id` وحده مفتاح منع التكرار؛ هذه مشكلة كُشفت في اختبار إدراك المحلي السابق.
- إعادة الربط لنفس المصدر تعيد استخدام سجله المنطقي أو تعمل مطابقة للهويات قبل الاستيراد.
- بدء المزامنة الأولى ثم مزامنة تلقائية احتياطية، مع دعم Webhooks الموقعة إذا كانت متاحة. **المسار العام في إدراك الحالي كان يرفض Webhooks بـ 501** حتى إضافة تحقق التوقيع، فلا توجه هذه الأحداث إليه دون تعديل مصرح به.
- توحيد المتجر والكاشير في تحليلات إدراك الحالية، والحذر من أن طلبًا واحدًا قد يمر من المتجر ثم الكاشير، فلا يُحسب مرتين.
- اختبارات E2E: بيع POS → لوحة إدراك، طلب أونلاين → لوحة إدراك، تغيير الحالة، مرتجع، فقد الاتصال وإعادة المحاولة، إعادة إرسال نفس الحدث، فصل وإعادة ربط نفس المصدر، والتحقق من المخزون حسب الفرع.
